Design — AsyncAPI Ownership Model

Each service owns the AsyncAPI spec for the channels it controls. The catalog crawls /asyncapi.json alongside /openapi.json from each server.

Ownership rules
📢 Broadcast (pub/sub)
e.g. outbox → Kafka funds.outbox
Anyone can subscribe, nobody is the single recipient
Owner: Producer
→ funds-main :3014
exposes /asyncapi.json
channel: funds.outbox
operation: send (publish)
message: FundsChanged
🎯 Point-to-point (command)
e.g. pg-boss queue leaderboard-update
One producer, one consumer — consumer defines the contract
Owner: Consumer
→ funds-main :3014 (pg-boss worker)
exposes /asyncapi.json
channel: pgboss/leaderboard-update
operation: receive (subscribe)
message: LeaderboardUpdateJob
Per-server AsyncAPI ownership in funds e2e
Server Channel Transport Operation Why this server?
funds-main :3014 funds.outbox Kafka (via Debezium) send Broadcast producer owns the contract
funds-main :3014 pgboss/leaderboard-update pg-boss receive P2P consumer defines expected message
funds-risk :3013 funds.outbox Kafka receive Subscriber documents what it expects
Catalog startup — crawl both spec types from each server
1. GET :3014/openapi.json → REST spec (funds-main)
2. GET :3014/asyncapi.json → Async spec (outbox send + pgboss receive)
3. GET :3013/openapi.json → REST spec (funds-risk)
4. GET :3013/asyncapi.json → Async spec (kafka receive)

No global asyncapi.yaml — each server owns its slice
