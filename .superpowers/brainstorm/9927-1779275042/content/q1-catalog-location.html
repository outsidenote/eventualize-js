Where should the service catalog live?

The funds e2e app currently runs two servers (main :3014, risk :3013). Where should the catalog UI be hosted?

A

Dedicated catalog server (e.g. :3099)

A 3rd server process in each e2e app, serving only the catalog UI. Reads routes/events from other servers at startup. Clean separation — catalog doesn't pollute business servers.

Pros

  • Zero coupling to business code
  • Can restart independently
  • Works even if main/risk servers are down

Cons

  • Another process to manage
B

Mounted on one existing server (e.g. GET /catalog)

The main server (or a new "gateway" server) serves the catalog UI at a sub-path. Routes from both servers are aggregated and served from one place.

Pros

  • Single URL to remember
  • No extra process

Cons

  • Catalog tied to one server lifecycle
  • Mixed concerns in server.ts
C

Shared package — each e2e app wires it in

A reusable @eventualize/dev-catalog package that any e2e app can install and mount. Each app registers its own routes/events, the package serves the UI. Designed to scale across multiple e2e apps.

Pros

  • Reusable across all future e2e apps
  • Consistent DX everywhere

Cons

  • More upfront work
  • Package versioning overhead
